Evals are fuzzy unit tests, and the judge can lie

An eval runs test cases through your agent, and a judge scores each answer against the policy. Before you trust the judge, check that it agrees with humans.

Why

Evals catch bad behavior before deploy; harnesses catch it at run time

The running example

A keyword check passes a wrong answer; a grounded judge does not

How evals lie

LLM judges have four biases that you must test for

Training the judge

Aim for 80–90% agreement with humans, not 100%

Have experts label about 30 question–answer pairs. Run the judge on the same pairs and count agreement. Human support teams agree with each other only about 80% of the time, so a judge near 100% is overfit to your examples.

Staying relevant

Give the judge the same policy search the agent uses

What to remember

Start cheap and add a judge only where you need one

  1. Climb the cost ladder: deterministic tests, then regex, then trace checks (which tools ran, how long), and a judge last.
  2. Write about 30 realistic cases and have a human label each one pass or fail.
  3. Score answers pointwise against the written policy, not pairwise. Use the cheapest judge model that works, from a different family than the agent, and pin its version.
  4. Run the eval in CI. Fail below 80% judge–human agreement, and treat 100% as a red flag.
  5. Retrieve the policy from one shared source (RAG) for agent and judge. Add new cases from production traffic.

Q&A · 54:32

Three audience questions

How do I grow the dataset before real users arrive?

Synthetic cases and red-team prompts

Generate adversarial prompts, then make more variants of the ones that fail.

Should I write evals for my Claude Code or Cursor skills?

No; write evals when you build a harness

Skills you write yourself are mostly deterministic code.

Should the judge and the agent share the policy?

Yes, one source of truth

Both query it, for example through OpenRAG. Keep the judge as close to the agent as you can.
