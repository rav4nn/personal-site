The harness, not the prompt, makes an agent reliable

A harness is the code around the model: tools, context, guardrails, the loop, and a verify step. In this talk, an old model learns to upvote a story on Hacker News, and the prompt never changes.

Why a harness

You rent the model, so reliability must come from your code

Think of a climbing harness. It ties you to the mountain, which does not move, so you do not fall. A dog harness keeps the dog from running off and, in his words, from bankrupting you with tokens. An agent harness ties a model that changes to code that does not.

Two meanings

“Harness” means two things, and this talk is about the agent kind

The demo

Same prompt, same old model, and only the harness changed

He builds a browser agent live. He picks an older model on purpose, and he does not change the prompt at any point. Each run adds parts to the harness.

The last run

The harness logs in, so the model never has to

Verify

Verify reads the trace, not the agent’s last message

The bare agent said it upvoted the story. It did not. A model’s report on its own work is not evidence. The trace is. It holds every tool call and every page the browser visited.

Takeaway

Fix behavior in the harness, not in the prompt

A login page, a loop that does not end, a history that grows too long, and a claim with no proof each have a part of the harness that fixes them in code. Code does the same thing every run. A longer prompt does not.

The demo used an old model on purpose. With a good harness, a smaller and cheaper model can do the job. He gave IBM’s open-source OpenRAG as an example of the same idea at company scale: a security harness around retrieval over private data such as PDFs, invoices, and call transcripts.

What to remember

Ground the model in code you control

  1. A harness is everything around the model: tool registry, context management, guardrails, the agent loop, and verify.
  2. Treat the model as a black box you rent. Do not rest reliability on the prompt alone.
  3. Put hard limits on every run, for example 15 iterations and 50 messages.
  4. Verify in code. Check the trace or the real state, never the agent’s own report.
  5. When the agent fails at a step that is the same every time, such as a login, handle that step in the harness and leave the prompt alone.

Practice

Which part of the harness fixes it?

Pick a part for each failure. “Prompt” is on the list too.

The agent goes back and forth between two pages and burns tokens for an hour.

Guardrails

A cap on iterations or messages ends the run. A prompt that says “do not loop” is a request, not a limit.

The agent says “Done, the form is sent.” Nothing reached the server.

Verify

Check the trace or the real state after the run. The agent’s last message is not proof.

After many tool calls, the agent forgets the task it was given.

Context management

Keep the system prompt and the task, and trim or compact the old tool output in between.

Every run stops at the same cookie banner.

Agent loop

This works like the login handler. The loop sees the banner, closes it with code, and tells the agent. No model call.

The task needs a PDF, and the agent has no way to open files.

Tool registry

Add a tool that reads files. The model cannot do what no tool lets it do.
